# scan — 扫描课件，构建课程大纲 + 心智模型

## Phase 0: 内容提取（脚本自动处理）

1. 检查 `output/{课程名}/raw/_manifest.json` 是否存在且文件一致 → 一致则跳过
2. 定位 Python:
   `which python3 || which python`，找不到则搜索常见路径
3. 运行:
   ```bash
   <python> ${CLAUDE_SKILL_DIR}/scripts/extract.py courses/{课程名} output/{课程名}/raw
   ```
4. 再跑裁图脚本（只读 PDF，可随时重跑；新课件到了加 `--only <文件名子串>` 只补那一讲）:
   ```bash
   <python> ${CLAUDE_SKILL_DIR}/scripts/extract_figures.py courses/{课程名} output/{课程名}/raw
   ```
   产出 `raw/figures/<stem>_p<N>_f<k>.png` + `raw/_figures.json`——每页的图形区域（位图 / 矢量簇 + 贴边标签）裁成独立图，供 story 直接嵌进正文（content-coverage.md §1.4 "原图优先于自绘"）。scan 阶段不消费它，只要确认跑过

> 📌 **两个脚本都传课程根目录，不要自己往下指**。它们共享同一套目录约定：
> - 有 `courses/{课程名}/lecture/` 就自动以它为课件根
> - `assignment*/`、`labs/`、`references/` 一律跳过（归 assignment 命令 / 只作深度指向）
>
> 这样课件从平铺整理进 `lecture/` 时，`raw/*.txt` 与 `raw/figures/*.png` 的**文件名保持不变** ——
> 已写好的 teach MD 里那些 `../raw/figures/...` 路径不会集体失效。
> 你要是绕过约定直接传 `courses/{课程名}/lecture`，结果一样；但传了根目录又手动加 `--recursive`
> 之类去抓 `assignment*/`，会把作业指导书的页码混进课件页码溯源里。
5. 脚本产出:
   - `raw/*.txt` — 每个文件的逐页文本
   - `raw/visuals/*.png` — 图重页截图。两条判据任一命中即截: ① 剔除页眉页脚模板行后正文<300字符且含位图或≥5条矢量绘图路径; ② 公式坍缩——正文里≤2字符的碎片行占比≥40%（数学课件的推导页文本层碎成一行一个符号，必须看图）
   - `raw/_visual_pages.json` — 需要 LLM 视觉描述的页面索引
   - `raw/_manifest.json` — 提取摘要
   - manifest 的 `skipped` 列表: 不支持的格式 + `references/` `books/` 子目录里的参考教材（几百页的书不是课件，不进教学管线；course-outline 里列为"参考书"供深度提示指向即可）

## Phase 1: 读取文本

用 Read 逐个读取 `raw/*.txt`。

## Phase 1.5: 视觉内容描述（按需，控制成本）

读取 `raw/_visual_pages.json`，获取图重页清单。

**成本控制策略:**
- 只对教学上有价值的图做视觉描述（架构图、流程图、对比图、数据图表）
- 跳过装饰性图片（人像、logo、截图没有信息增量的页面）
- 判断方法: 看 _visual_pages.json 中的 text_extracted 字段
  - 如果已有文本能说明内容 → 跳过
  - 如果文本几乎为空且来源是正课 Lecture → 用 Read 查看 PNG，用一句话描述图的内容
  - reason 里的 bitmap/vector 标志可辅助判断: vector=True 的多为文本已可重建的简单示意图，跳过率高；bitmap=True 且文本近空的往往是必看的架构图/截图
- 描述写入 `raw/_visual_descriptions.md`（按源文件分节、逐页一行 `- pN: [图: 一句话描述]`）。**不要追加进 raw/*.txt** — raw/ 是 extract.py 的可重生成产物，重跑会覆盖追加内容，且会让文件与 _manifest.json 记录不一致触发误判重提取

**典型需要描述的图:**
- 架构图 (architecture diagram)
- 流程图 (flowchart / pipeline)
- 对比图 (comparison chart)
- 层级/拓扑关系图 (hierarchy / topology)

**典型可跳过的图:**
- 人像照片、logo
- 纯表格（OCR 通常能提取）
- 网页截图（URL 已在文本中）

**消费必须留痕**: 对 _visual_pages.json 里的每一页，"看了并追加描述"还是"跳过 + 理由"，都要记录下来——Phase 2.5 的覆盖审计要求逐条对账（此前 400+ 张截图零消费痕迹，无法证明图里的知识进了教学链）。

## Phase 1.6: 讲者脉络（每讲一份，并行）

关键词和定义人人能讲，一门课独有的是**主讲人怎样把它组织起来**：开场问题、为什么从 A 转到 B（"Why …?""Limitation""Fallacy""But:" 这类过渡页）、每个例子承担哪一步、老师的直觉原话、哪里埋伏笔。这些散在路标/过渡/学习目标/总结页里——它们在 Phase 2.5 是豁免页，但在这里是主要证据。

- 按 `.claude/skills/full-learn/templates/lecture-flow.md` 每 2–3 讲派一个 agent 并行，产出 `output/{课程名}/lecture-flow/L{N}.md`（与 full-learn 共享，已存在且课件未变就跳过）。
- 每份逐步评价老师讲得好 / 跳步 / 缺动机：下游默认沿用老师的讲法，按评价有理由地改进，不照抄也不推翻。
- 收回后抽查：每讲 3 条引文或数字回原 PDF 核对。

## Phase 1.A: 作业/项目材料（如果 courses/{课程名}/ 下有 .ipynb / .py / 代码文件夹）

**判断材料类型**: 扫描 courses/{课程名}/ 下的文件（含 `assignment*/` 子目录 —— 它们不进 extract.py 管线，但 scan 要知道它们存在）。如果发现 `.ipynb`、`.py`、`docker-compose.yml`、`Makefile`、`requirements.txt` 等代码/配置文件 → 进入本流程。和 Phase 0-1 的课件提取**并行**，不互斥。

**LLM 直接读取**（不需要 extract.py）:
- `.ipynb`: 用 Read 直接读（Claude 原生支持 notebook，代码+输出+markdown 全能看到）
- `.py` / `.java` / `.js` 等: 用 Read 直接读
- `.pdf`（作业说明）: 用 Read 读 PDF 或先跑 extract.py 提取文本
- `requirements.txt` / `package.json` / `docker-compose.yml`: 用 Read 直接读

**四层递进分析**:

对每个作业/项目文件夹，按以下四层由浅入深分析:

### Layer 1: 全貌 (What) — "这个作业/项目在做什么"

- 读 README / 作业说明 PDF / notebook 顶部的 markdown block
- 读依赖文件（requirements.txt, package.json）→ 识别技术栈
- 读目录结构 → 推断组织方式
- **产出**: 一段话概括"这是一个用 X 技术做 Y 事情的 Z"

### Layer 2: 设计决策 (Why) — "为什么这样做"

- 读代码中的关键选型:
  - 用了什么框架/库？为什么选它而不是替代品？
  - 数据怎么组织的？为什么这样分表/分文件？
  - Pipeline 怎么串的？每一步为什么在这个位置？
- 读 notebook 中的注释和 markdown（作者的思路说明）
- **产出**: 每个关键选型一条 "选了 X，因为 Y，替代方案是 Z"

### Layer 3: 实现逻辑 (How) — "代码怎么工作的"

- 读核心函数/类的逻辑流程
- 数据处理链路: 数据从哪来 → 经过什么变换 → 最终输出什么
- 错误处理 / 边界情况 / 性能考量
- **产出**: 关键代码段的"白话翻译"（一段代码 → 一句话说它在干什么 + 为什么这样写）

### Layer 4: 细节 (Deep) — "具体到行级别"

- 特定算法的实现细节
- 参数选择的依据（如 `maxIter=50, maxDepth=8`）
- 评估指标的含义和判读
- 可改进的地方
- **产出**: 针对答辩/面试的"如果被问到这个细节，怎么回答"

**四层产出都进入 concepts.json** — 每层的知识点用 tag 标记层级:
- `layer:what` / `layer:why` / `layer:how` / `layer:deep`
- 后续 story 命令按层递进组织教学

## Phase 2: 知识提取

从文本+图描述+代码分析中提取:
- 章节结构（课件）/ 任务结构（作业）
- 核心概念和定义
- 关系（依赖、对比、组成）
- 技术选型和设计决策（作业/项目）
- 考试重点（如有往年考题）

逐页/逐 cell 过一遍，不跳。

**concepts.json 中每个 KP 必须带 `source` 字段**（文件名 + 页码范围，如 `"L7 p1-33"`），这是 Phase 2.5 覆盖审计的对账依据。

**页码一律用物理页码**（raw txt 的 `--- Page N ---` 编号）。幻灯片页脚上印的编号可能因隐藏页与物理页错位，不要用它——下游 teach 引用页码时读者按 PDF 物理页翻找。

**concepts.json 最小 schema**（其余字段按课程材料按需加，如 exam_date/tutorials）:
```json
{
  "course": "...", "scan_date": "...", "materials": [...],
  "arcs": [{
    "id": 1, "name": "...", "sources": ["L1 p3-20"],
    "concepts": [{"id": "KP-1.1", "name": "...", "source": "L1 p3", "key": "一句话核心认知"}]
  }],
  "exam_high_points": [...]
}
```
concept 的 `id/name/source/key` 四字段必需；有依赖关系时加 `deps: ["KP-x.y"]`。

## Phase 2.5: 覆盖审计（硬门禁，不可跳过）

> 为什么有这个 gate: 一次真实失败——某课 L7 实为三讲合一（204 页），知识提取只建模了前 46 页，
> 后 158 页（含老师自出的考题组）静默蒸发，下游 story/outline 全链条盲区，无人发现。
> "逐页过一遍，不跳"是意愿不是保障；这个 gate 把覆盖变成可对账的事实。

知识提取完成后，产出 `output/{课程名}/coverage-audit.md`，做**页→KP 反向对账**:

1. 对每个 `raw/*.txt`，列出总页数（数 `--- Page N ---` 标记）。
2. 把每页归入且仅归入一类:
   - **已覆盖**: 该页内容映射到 ≥1 个 KP（从 concepts.json 的 source 页码范围倒推）
   - **显式豁免**: 封面 / 目录 / 分节页 / 学习目标·路标页 / 总结页(内容为已建 KP 重述) / 致谢·参考文献 / 纯 logo / 与前页重复的动画帧 — 必须写明豁免理由
   - **未覆盖**: 两者都不是 → 这就是漏洞

   > 这个 gate 管什么、不管什么: 它防的是**整块蒸发**（几十页没建 KP 而无人发现）；防不了 source 页码区间内的"混水页"（区间里某页只弱相关也算已覆盖）。后者靠 Phase 2 的"逐页过一遍"和 story 的保真门禁兜底。
3. 报告格式（每个源文件一行汇总 + 未覆盖页明细）:

```markdown
# {课程名} 覆盖审计

| 源文件 | 总页数 | 已覆盖 | 豁免 | 未覆盖 | 覆盖率 |
|--------|--------|--------|------|--------|--------|
| L7.txt | 204 | 46 | 4 | 154 | 23% ❌ |

## 未覆盖页明细
- L7 p47-144: 某开源框架源码精读 — 未建 KP ← 必须处理
## 豁免明细
- L7 p1: 封面
## 图重页消费记录
- _visual_pages.json 共 N 页; 已 Read 并写入描述 M 页; 判定跳过 K 页(逐条理由)
## 未进管线文件（来自 _manifest.json 的 skipped）
- xxx.ipynb → 已按 Phase 1.A 直接 Read / 未处理(理由)
```

4. **门禁规则**: 任何源文件"未覆盖"页 > 10% → 回到 Phase 2 补提取（或给出成块豁免的明确理由，如"该 lecture 声明不考"——豁免理由必须写进报告，且只有用户可以批准超过 10% 的成块豁免）。**不允许静默通过。**
5. 同时对账 `_manifest.json` 的 `skipped` 列表：每个被跳过的文件要么按 Phase 1.A 处理，要么在报告中留下未处理记录。

## Phase 3: 产出三个文件

### 文件 1: `output/{课程名}/course-outline.md` — 课程大纲

这是目录性质的索引，让人知道"这门课有什么"。

```markdown
# {课程名} 课程大纲

## 元信息
- 来源 / 扫描时间 / 模块数 / 知识点数

## 模块结构
### M1: {名称}
- 来源: {文件} p.X-Y
- 知识点: KP-1.1, KP-1.2, ...

## 学习顺序 (拓扑排序)
## 考试重点 (如有)
```

### 文件 2: `output/{课程名}/mental-model.md` — 心智模型

**这是核心产出。** 目标: 一个人读完这份文件，20分钟内建立对整门课的完整核心认知。

它不是知识点列表，而是一个**连贯的认知网络**:
- 先给一句话回答"这门课到底在讲什么"
- 然后用 3-5 个核心问题串联全课（为什么→是什么→怎么做→怎么管→花多少钱）。**问题链从讲者脉络提炼**：优先用老师的开场问题和过渡页原话（标页码），概念的直觉优先用老师的例子；老师没给的才自己补
- 每个问题下，只放最核心的概念，用**直觉+一句定义+和其他概念的关系**表达
- 概念之间的依赖/对比/组成关系用箭头或缩进体现
- 最后给一张 ASCII 全局关系图

格式:

```markdown
# {课程名} 心智模型

> 一句话: {这门课到底在讲什么}

## 核心问题链

### Q1: {为什么需要云计算？}
{2-3句话回答，串联关键概念}
- **概念A** (English) — {直觉} | 关联: → B, → C

### Q2: {云计算怎么分类？}
...

## 关键对比 (容易混淆的概念)
| A | B | 核心区别 |
|---|---|---------|

## 全局关系图
[ASCII 图: 所有核心概念的关系网络，标注依赖/对比/组成]

## 考试速查 (如有)
[高频考点 + 一句话答案]
```

### 文件 3: `output/{课程名}/concepts.json` — 结构化数据

(同之前的 schema，供 teach/quiz/where 等命令使用)

## Phase 4: 展示

1. 展示心智模型的全局关系图
2. 简要说明: 几个模块、多少知识点
3. 问用户: 想从哪个问题开始深入？
